# 项目知识格式 v2 与维护能力详细设计

本文保留v2阶段设计历史；当前源码的轻量格式v3见[优化方案](project-knowledge-lightweight-design.md)。

日期：2026-11-03。状态：**设计已批准；已实现并完成合成自测，未安装或发布。**

实际验证见[开发自测](development-validation.md)。本文是四类资料的格式、维护和共用读取契约的设计源。Ego负责的使用阶段、提示词和CLI接入在相邻仓库 docs/v0.1.9-project-knowledge-v2-integration-design.md，本文不承担测试运行时编排。所有示例均为完全合成内容，不来源于真实项目、账号或业务资料。

## 1. 目标与设计边界

每个项目围绕四项资料组织：功能地图、项目通用规则、账号配置、项目配置。用户通过自然语言给出知识库本地根目录；维护AI整理候选和来源，使用方AI按实际任务选择相关内容。

- JSON为AI及程序读取的唯一主数据；自然语言业务正文可使用Markdown排版，存放在JSON文本中。
- Markdown/HTML仅为可选阅读导出，不是另一套可独立修改的业务事实源，不作为每次维护的默认产物。
- 地图回答“哪个应用/页面、哪个模块入口”；不保存CSS、XPath、坐标、逐按钮脚本或完整功能规格。
- 通用规则允许详细：同一角色的允许、禁止、范围、例外与依据应完整表达；不以“轻量”为由仅写一句原则。
- 账号描述已声明的测试身份及限制，项目配置描述环境和页面地址；两者都不代替本轮登录、实际授权和业务验证。
- 工具做数据事务、引用及完整性检查。AI决定提取、检索、账号选择、导航、补读、重试及结论。
- 本版不建设向量数据库、在线知识服务、全局项目注册中心、页面爬虫或密码管理系统。

## 2. 当前基础与版本决策

本次优化前的v1将feature、role等条目和规则陈述放入topics，scope放在knowledge.json；本次在已有初始化、增量保存、恢复与三方比较基础上实现v2。当前代码见[格式定义](../src/contract.mts)、[存储](../src/store.mts)、[写事务](../src/writer.mts)、[三方比较](../src/changes.mts)。

v2将入口、页面和账号信息从自由文本中独立出来，允许四类资料被精确读取。因此明确使用knowledgeFormatVersion=2、knowledgeReadVersion=2。软件版本、格式版本、业务资料版本继续分别管理，本文不决定发版或Tag。

用户已明确：本Skill尚未正式投入使用，本次优化不要求兼容旧有资源。v2的结构、字段、状态和接口按当前目标设计，不增加v1兼容解析、双轨读写、字段映射转换器或旧目录适配。已有实现中仍适合新目标的校验和事务能力可以复用，不因沿用某个名称或工具就视为兼容要求。

后续另行授权知识构建时，由AI依据原始资料及审核结论直接生成符合新格式的知识文件；不要求把旧知识文件机械转换成新结构，也不把旧资源一一映射作为验收条件。本轮仍只优化Skill，不执行知识重新生成。现有试验资料和历史记录保留，不因无需兼容而删除或覆盖。

当前已安装工具仍只支持v1；实现及安装完成前，不能把v2设计声称为已可用能力。新版工具遇到旧格式时明确说明该来源不受支持，不静默猜读、转换或重写。

## 3. 固定目录与四类资料

```text
<用户明确选择的知识库根目录>/
  knowledge.json                 项目身份和格式
  project.json                   环境、应用、页面、可复用适用范围
  feature-map.json               模块、入口、关联规则、入口观察
  rules/<topic-id>.json          按主题维护通用规则及角色
  accounts.json                  非秘密测试账号信息
  sources/<source-version-id>.json 确定版本资料及观察出处
```

四类是逻辑职责，不要求为每个功能建立目录。地图和账号先各用一个文件；规则按公共主题拆分以便Git协作。所有可独立维护的模块、入口、页面、规则、陈述、角色、账号、绑定、检查和问题都有稳定ID。

允许空库：init只生成knowledge.json和空的project.json。feature-map、rules、accounts、sources尚未配置时可缺省；不造业务内容或秘密。四类资料既不必一次齐全，也不作为测试运行的强制前提。

维护受管集合严格限定为上述JSON路径。阅读导出、测试证据、原始资料、私有凭据及临时请求不参与知识快照；它们在用户确认的库外私有位置保留。

## 4. 共用元数据与适用范围

### 4.1 身份、类型与状态

knowledge.json仅保留knowledgeFormatVersion、knowledgeId、projectId、projectName、createdAt。项目ID不因改名改变，知识库ID不因维护重新生成。

共用Meta用于一段陈述或一个可独立更新的配置记录：

| 字段 | 约定 |
| --- | --- |
| state | confirmed / observed / pending；分别表示有明确确认依据、限定条件下的观察、待确认 |
| lifecycle | active / superseded / retired |
| sourceRefs | sourceId与精确locator；confirmed和observed必须有有效来源 |
| updatedAt | 内容或依据实质变化的时间；不把整批导入时间当作来源发布时间 |
| changeReason | 本次实质变化的原因 |
| limitations | 已知局限，不默认解释为数据已经就绪 |

采用通用state是为了同时表达规则、入口、地址和账号配置。confirmed不代表线上已部署或实际账号有权；observed也不自动成为规则。新规则仍保留人工审核边界。

Statement为id、text、scopeIds、meta、relations、issueIds。text保存完整业务描述；relations沿用requires、uses_role、operates_on、affects、navigates_to、related_to，最后一项不推导前置步骤。

### 4.2 scope与组织授权范围分开

project.json.scopes保存可引用的适用范围：

- id、description：稳定身份及人可读说明。
- environmentIds、applicationIds：null为未知；仅含“*”表示有依据的全部适用；否则为非空ID列表。“*”不能与其他ID混用。
- versionNote：明确的软件/规则版本限制说明，可为null；本版不做自然语言版本条件的自动业务裁决。
- meta：适用范围本身的确认状态、来源与变化依据，遵守共用Meta。

scopeIds为空表示未登记适用范围，不表示所有环境。环境/应用匹配可由工具按ID判断；版本适用性仍由AI根据来源核对。软件版本未知只返回局限，不让所有公共规则读取失败。

账号的roleBindings.scopeDescription/scopeRefs描述组织、项目等业务授权范围，与上述环境/应用适用范围不是同一维度；不把scope做成一套通用IAM引擎。

### 4.3 来源与问题

Source继续使用id、documentId、title、kind、version、issuedAt、sha256、locator、limitations；kind沿用requirement/manual/observation/confirmation/other。同一资料的新版本创建新Source ID，不修改旧ID的资料身份、版本、SHA或定位含义。

Issue为id、type、recordIds、summary、sourceRefs、resolution。type沿用conflict/stale/needs_review/missing；recordIds可引用模块、陈述或配置记录；resolution非空须有解决依据。结构正确与业务矛盾分别记录，代码不自动裁定谁正确。

## 5. 项目配置 project.json

| 集合 | 字段与职责 |
| --- | --- |
| environments | id、title、aliases、defaultHomePageId、defaultLoginPageId、meta；默认页可为null |
| applications | id、title、aliases、meta；描述不同应用/页面体系，不重复维护每个模块的URL |
| pages | id、title、kind、applicationId、environmentId、url、openMode、meta |
| scopes | 第4.2节的范围记录 |
| issues | 影响配置的已知问题 |

pages.kind为home/login/feature；url为稳定HTTP(S)地址或null。openMode为direct/via_ui/manual：分别表示已有依据的直接入口、应从产品UI进入、需用户处理的入口。该字段给AI提供提示，不自动启动浏览器。

- 一个项目可以跨多个应用、域名和环境；同一逻辑模块可引用多页。
- 实际登录URL未知时留空，不把首页或一次性SSO跳转猜成登录URL。
- URL不保存一次性code、Token、Cookie、用户密码或嵌入式认证参数；必要动态参数由既有登录过程取得。
- 地址只是导航资料，不授予访问权限。不因本地缺少登录页配置而判项目不可测试。
- pages引用真实的environment/application ID；默认页必须属于对应环境。未知页允许记录pending和null URL，读取时注明无法直接定位。

## 6. 功能地图 feature-map.json

feature-map.json顶层为domains、modules、checks、issues。Domain为id、title、aliases，保留功能分组稳定ID。

Module字段：id、domainId、title、aliases、summary、descriptions、entryPoints、ruleIds、roleIds。domainId引用一个Domain，未知时可为空；descriptions为有来源的Statement。不为按钮和字段创建模块。

EntryPoint字段：

| 字段 | 含义 |
| --- | --- |
| id | 稳定入口ID |
| pageId | project.pages中的页面ID；未知可为null |
| menuPath | 模块级文字路径数组，例如“示例门户→示例工作区→示例馆藏” |
| accessNotes | 入口条件与特殊情况的人可读提示，不执行权限计算 |
| scopeIds、meta | 入口的适用范围、状态及出处 |

单模块可以有多个entryPoints，以表达在多个页面/环境中的入口。URL只在project.pages维护，地图引用pageId。允许有URL没有菜单路径，或需要UI进入而不能直接跳转。

entryPoints为空仅表示未登记入口。只有有明确资料说明时，descriptions才可写“无独立UI”；不能从没找到入口推断功能不存在。地图不包含固定测试步骤，不决定每轮应点哪个按钮。

### 6.1 入口观察 Check

feature-map.json顶层另有checks和issues。Check字段为id、targetId、environmentId、accountId、actorNote、outcome、coverage、observedAt、description、sourceRefs、limitations。

- outcome为verified/violation/inconclusive/not_tested，对应已验证/发现违反/无法判断/未测试。
- coverage是AI明确写出的观察范围，例如“入口可见”或“页面可达”；不从工具动作推断业务通过。
- targetId指Module或EntryPoint；accountId可空，actorNote说明当时身份及限制。
- observedAt无法从真实来源确定时留空，不用文件mtime补造。
- 检查记录是历史观察，保留原来源；入口或配置变化后，旧检查不能自动证明新入口仍可达。
- 检查中使用证据Source引用库外原件，不复制截图、登录参数或原始业务数据进通用工具仓库。

## 7. 详细通用规则 rules/<topic-id>.json

Topic为id、title、entries、issues。Entry为id、kind、title、aliases、summary、moduleIds、businessTags、statements；kind只用rule或role，明确区分一般规则与角色定义。

建议完整正文包含：适用对象与业务含义、允许行为、禁止行为、组织/对象/数据范围、例外与生效条件、关联公共规则及原文位置。正文不强制套固定章节，也不拆成逐操作的权限布尔表。

- 一份角色正文可覆盖多个模块，moduleIds建立检索关系；没有明确模块时仍可按别名和businessTags查。
- 账号引用角色ID，不抄一份角色全部权限；角色引用其他通用规则时同样保留ID关联。
- 角色不同部分可分别confirmed/pending，读取不能把整份角色概括成全部已确认。
- 用户的新有效需求与旧规则不一致时，保留双方来源和适用范围；不能按时间较新、界面当前可操作或更容易测试来选标准。
- 功能字段、页面控件、单功能所有分支、完整用例仍留原需求。跨项目测试方法仍属于Ego自身指南。

## 8. 测试账号 accounts.json

顶层为accounts、checks、issues。Account字段为id、alias、environmentId、loginName、loginMode、credentialRef、roleBindings、restrictions、meta。

RoleBinding为id、roleId、scopeDescription、scopeRefs；scopeRefs仅是type/id/label的已知对象标识列表，不计算组织继承或权限并集。未知授权范围在scopeDescription明确写未知，不自动视为全局。

| 设计点 | 决定 |
| --- | --- |
| 同一人跨环境 | 各环境的Account记录分开，可同loginName；不能默认凭据和角色一致 |
| 同一账号多身份 | 多个roleBindings分别记录范围；不自动合并成更大权限 |
| loginMode | manual / existing_session / credential_ref |
| credentialRef | null或逻辑凭据引用ID，不能是明文、URL或本机秘密文件路径 |
| restrictions | 场景限制、禁止用途等明确约束；不是授予新操作的授权书 |
| checks | 复用Check，记录当时核对范围；旧结果不证明本轮已登录或角色仍有效 |

本版只表达凭据引用，不新建密钥托管/解密系统。实际登录复用用户已允许的既有安全方式；无可用解析设施时，credential_ref不被谎报为可自动登录，可转用户手动登录。

查询摘要默认只给alias、环境、声明角色、范围与限制；精确read账号才返回loginName与逻辑credentialRef。所有读取均不解引用、不加载密码、Token、Cookie或会话文件；不因读取role而反向展开所有账号。

## 10. 写入、历史与Git冲突

维护CLI保留init、validate、save、compare、recover，不新增业务决策器。

- init默认生成身份和空project集合；是否同时建其他空集合由用户任务决定，不造默认账号或网址。
- save继续接收projectId、knowledgeId、expectedSnapshotSha256、files、reason、backupDir。files扩展到固定v2集合；未声明路径、路径穿越、符号链接/联接绕行仍拒绝。
- 写入校验全库ID唯一、外键、元数据、来源、状态和必要秘密模式；确认/观察无来源、confirmed仅有observation来源、同一ID改指其他资料版本均不接受。
- 写事务沿用prepared标记、暂存、逐文件读回与显式恢复。未由干净Git保留的旧文件仍须在库外备份；不能只靠.gitignore。
- 原ID更新保留ID和变化原因；退出的规则/模块等用retired或superseded及来源保留。移除绑定/关系的旧内容也必须有Git或外部前版依据。
- compare按Header、记录ID及容器成员关系比较四类资料。业务源ID、URL或角色范围的双边变化列为冲突候选；不采用最后时间戳胜出，不自动执行Git合并。
- Git状态、固定提交读取、工作区重检和快照指纹纳入project.json、feature-map.json、rules、accounts、sources；不只扩展JSON解析却漏掉Git检测和恢复路径。
- 目录读取继续沿用当前1MiB单文件、16MiB总受管数据、512文件的明确边界；超限说明范围，不悄悄截断知识。
- 不自动创建远端Coding仓库、同步、提交、推送或发布；共享前按实际授权逐文件审查真实资料和账号标识。

## 11. 只读接口的共用保证

Ego保留inspect/query/read，运行时无需加载维护Skill。读取契约按category=project/modules/rules/accounts选择；rules内按kind=rule/role区分。完整请求和可选行为以Ego集成设计为准，字段含义不能由两端另造一份。

共用保证：

1. inspect返回身份、类别存在性、数量和版本摘要，不返回所有正文、账号标识或秘密引用。
2. query返回短摘要、状态集合、命中位置与可读引用，read才展开选中的详细内容。
3. 关联方向为模块→页面/规则/角色、账号→角色、规则→显式引用；默认不反向扫出全部账号。
4. 可选知识不可用不变成测试门禁；项目不匹配仍不返回该库业务内容。
5. 元数据校验不证明内容正确、账号有权、页面可达或业务通过。
6. 返回实际使用文件SHA、内容指纹、来源、Git/草案和截断信息，不声称已获取公司远端最新状态。
7. 维护端validate仍是显式严格校验；消费端可以在一个类别损坏时只使用独立有效类别，两者不混为同一个valid=true。

## 12. 本轮范围：只优化Skill

本轮只设计并实现Skill自身的格式、维护、读取及提示词能力。**不设计真实知识库知识的更新、迁移、重组或正式目录切换方案。** 不补写真实角色正文、不调整现有功能地图、不配置真实账号或网址。

现有知识数据、历史摘录和已安装Skill保持原样。后续可由AI按新格式重新生成知识文件，但本轮不安排真实知识重建或旧库更新方案，也不以本设计为自动处理现有库的授权。

v2写入和读取只使用完全合成库验证；不把真实项目知识、账号配置、UI证据或原始资料放进通用工具仓库。本文中的结构示例不构成真实知识整理任务。
