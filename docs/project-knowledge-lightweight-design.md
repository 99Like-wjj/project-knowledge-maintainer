# 项目知识轻量化优化方案

日期：2026-11-03。状态：**设计已批准；已实现格式v3并完成合成自测，未安装或发布。** 更新：2026-11-04。

本方案修订[四类知识v2设计](v0.1.9-project-knowledge-v2-detailed-design.md)。本文只定义维护Skill的职责和共用格式；Ego的读取与使用见[使用方方案](../../ai-autonomous-testing-ego-lite/docs/project-knowledge-lightweight-integration-design.md)。示例完全合成，不来源于任何真实项目。

## 1. 目标和范围

保留功能地图与通用规则的稳定结构，把账号配置、项目配置改为用户提供资料、AI整理登记的轻量记录。用户用自然语言、现有表格或配置说明提供内容，不需要手写JSON。

实现范围为维护Skill及Ego读取端；实际项目知识、安装目录和历史资料保持原样，未生成候选安装包或发布版本。

| 资料 | 格式策略 | 默认内容来源 |
| --- | --- | --- |
| 功能地图 | 固定模块用途、所属应用/页面、模块级入口及规则关联；不细化到按钮 | 用户指定需求、源码线索和获准的页面观察 |
| 通用规则 | 固定条目、陈述、来源、确认状态；适用范围和业务正文用自然语言 | 用户指定有效资料，按任务要求审核 |
| 账号配置 | 固定极少数检索字段，业务属性自由 | 用户提供的实际账号说明 |
| 项目配置 | 与账号共用轻量记录，业务配置自由 | 用户提供的地址、登录说明及其他配置 |

默认不分析PRD或代码来推导真实账号、实际授权、环境部署或完整配置清单。用户另行要求分析测试需要哪些身份时，可以开展该测试准备任务；分析结果是准备建议，不是已存在的账号。

## 2. 保留四类目录，取消配置之间的强依赖

~~~text
<用户知识库根目录>/
  knowledge.json
  feature-map.json
  rules/<topic-id>.json
  accounts.json
  project.json
  sources/<source-version-id>.json
~~~

- knowledge.json继续记录项目/知识库身份、创建时间和格式版本。
- feature-map与rules仍是结构化知识；sources继续为需要追溯的规则与观察保存确定版本依据。
- accounts.json和project.json均为{"items":[]}，可以缺省或为空。
- 不要求先建环境表、应用表、角色表、组织表或页面表才能保存配置。
- 初始化仍只生成身份和空project.json；不生成账号画像、默认业务字段或缺项问题列表。
- 用户提供多少登记多少。信息未提供可省略，不补成确定事实，也不为了凑齐格式逐项追问。

## 3. 两类配置共用最小记录

每条记录仅有两个必填字段。它们由AI整理生成，不要求用户填写技术标识。

| 字段 | 要求 | 用途 |
| --- | --- | --- |
| id | 必填，由AI生成并在后续维护时保留 | 精确定位、版本比较 |
| title | 必填 | 用户能识别的账号别名或配置名称 |
| summary | 可选，AI可忠实概括已有说明 | 短摘要，便于检索；不补推权限或配置 |
| tags | 可选，自由字符串，不预置角色/环境枚举 | 环境、用途等搜索线索 |
| description | 可选，自然语言，可含Markdown | 权限、限制、登录说明或其他文字 |
| properties | 可选，自由JSON对象 | 保留项目自有字段名称、嵌套结构和值 |

外层提供稳定检索入口，业务字段放入properties，不因项目增加字段而修改Schema。summary与tags只是检索提示，不形成第二套授权依据；详细说明在read时一起读取。即使只有别名或配置名称，也允许先登记。

不强制loginName、loginMode、environmentId、roleBindings、scopeRefs、credentialRef、restrictions或Meta。用户确实提供的同类信息可按原意放入description/properties；没有单独来源记录或正式角色条目也能保存。

### 完全合成账号示例

~~~json
{
  "items": [
    {
      "id": "fictional-reader-a",
      "title": "完全合成阅览账号",
      "summary": "演示环境的阅览身份，仅访问合成馆甲。",
      "tags": ["演示环境", "阅览者"],
      "description": "由用户人工完成登录；不具备馆藏维护权限。",
      "properties": {
        "登录标识": "fictional-reader-a",
        "使用范围": "完全合成馆甲",
        "项目自有属性": {
          "演示分组": "fictional-group-a"
        }
      }
    }
  ]
}
~~~

### 完全合成项目配置示例

~~~json
{
  "items": [
    {
      "id": "fictional-lab",
      "title": "完全合成实验环境",
      "properties": {
        "首页": "https://reading.example.invalid/",
        "登录说明": "人工完成登录后继续",
        "附加配置": {
          "演示区域": "fictional-wing-a"
        }
      }
    }
  ]
}
~~~

这些只是示例字段，不是模板必填项。另一个项目可以用不同的字段和说明方式，也可以用多条记录分别描述不同站点、应用或环境；不要求嵌入固定层级。

账号配置仍不保存密码、Token、Cookie等秘密；可记录非秘密登录说明或既有逻辑引用，工具不解析引用或自动登录。自由字段不是可执行脚本。

## 4. 对地图和规则只做必要解耦

账号/项目配置变轻后，不把原强依赖转移到另一张注册表。

| 当前依赖 | 调整后的表达 |
| --- | --- |
| 账号roleBindings必须引用已有角色 | 账号直接保留用户声明的身份/限制；不要求创建角色档案 |
| 地图entryPoint.pageId引用project.pages | 入口内直接保存可选application、page、url，以及既有menuPath/accessNotes |
| 陈述scopeIds引用project.scopes | 陈述改用可选appliesTo自然语言说明，记录环境、版本及业务边界；省略表示未说明，不表示全部适用 |
| 历史检查必须通过环境/账号ID说明上下文 | 用description/actorNote保留当时环境和身份，不依赖配置条目；保留targetId、outcome、coverage、时间和来源 |

地图的模块、用途、来源、入口、ruleIds/roleIds等职责不变；有明确关联的规则/角色继续引用，没有则留空。角色规则仍可写完整允许、禁止、范围和例外，但不为每个账号自动建一份角色规则。

模块有多个页面时分别登记入口。页面名称和模块路径足以定位时，不要求URL；已知稳定直达地址可以记录。项目配置主要登记用户给的站点/环境信息，地图通常只需写所属应用、页面和模块路径。

完全合成的入口定位字段片段：

~~~json
{
  "application": "完全合成阅览门户",
  "page": "馆藏页",
  "menuPath": ["工作台", "馆藏"],
  "accessNotes": "从工作台按UI进入。"
}
~~~

这是定位字段片段，不是完整入口对象；既有入口ID和来源元数据仍保留。不同环境的入口有差异时，分别写明适用范围，不由工具推导等价环境、权限并集或用户应走的路径。

## 5. 维护与校验的边界

| 保留 | 本次删除或放宽 |
| --- | --- |
| 项目身份、JSON可读性、记录ID唯一、文件大小/路径边界 | 配置业务字段白名单、角色/环境等必填外键 |
| 地图/规则内部的必要引用与来源校验 | 账号配置绑定完整角色/组织模型 |
| 快照指纹、保存读回、中断恢复、Git或外部前版保留 | 给每条配置套confirmed/observed/pending、来源档案及生命周期 |
| Git三方差异与来源冲突依据 | 从PRD推导“必须准备多少账号/环境”的默认流程 |

账号/项目配置按用户明确指令可以修正或移除，旧文件通过Git或外部备份保留，不强制留下retired条目。规则、来源和历史观察仍遵守原有保留要求。

比较配置版本时，按稳定id比较记录和自由内容，列出双方改动；内容含义由AI结合用户说明判断。不设计属性映射器或业务合并引擎，不按最后时间戳自动选正确版本。

没有账号、没有独立登录地址、没有部署版本或未提供额外属性，不自动生成missing问题。只有本次明确任务实际依赖某项而资料不足时，才集中说明影响和需要补充的信息。

## 6. Skill如何工作

- 整理规则/地图：按用户授权分析指定资料，保留来源、适用边界和审核状态。
- 登记账号/配置：读用户提供的内容，忠实整理成轻量记录；可生成检索摘要，保留原意与自定义字段。
- 维护更新：识别用户指向的记录，展示存在歧义或冲突的部分；不把普通文字整理变成完整权限审计。
- 交付：给实际保存位置、变化和当前任务相关缺项。用户未要求时，不默认生成全项目准备清单或HTML。

这些是职责提示，不是固定阶段门禁。CLI继续使用init、validate、save、compare、recover，不增加注册中心、自动采集器或安装工具。

## 7. 版本和实现范围

采用knowledgeFormatVersion=3、knowledgeReadVersion=3，软件版本独立管理。变更涉及project/accounts结构、地图页面引用及规则适用范围，不能只改提示词后继续宣称v2兼容。

按当前目标原生实现v3，不增加v1/v2兜底、双轨读写或转换器。现有资料和历史不会因格式变化自动删除、覆盖或重建；本文不安排真实知识库的更新或目录切换。

维护端只调整现有contract、Schema、store、writer、changes、Skill指南及合成示例/测试；Ego调整对应共用副本、读取命令、指南和相关回归。复用当前事务和读取框架，不重写工具体系。

相较v2，确定性环境/角色外键过滤会减少，配置的业务含义更多由AI读取说明后判断。稳定标识、可选摘要/标签、按需精确读取用于控制检索成本；本方案不引入向量检索或字段查询语言。

## 8. 实现后的验收

下表为验收条件；实际结果见[开发自测](development-validation.md)，工程通过不等于真实业务验收。

| 场景 | 应观察到的结果 |
| --- | --- |
| 只有账号别名，无环境/角色档案 | AI可生成合法最小记录并保存，不要求补齐外键 |
| 两个项目使用不同自定义属性和嵌套结构 | 保存、比较、读取后内容完整，不要求改Schema |
| 用户只给一个首页和登录说明 | 可保存项目配置，不要求建全套页面/应用表 |
| 未配置账号或项目配置 | 地图、规则仍可使用，不自动产生全库准备任务 |
| 模块入口没有配置文件或页面ID | 按模块内所属应用/页面及路径可读取导航 |
| 规则只声明自然语言适用范围 | 原文、来源和状态可读，不要求环境/范围注册表 |
| 账号检索与精确读取 | 摘要不回显登录标识或自由配置，精确读取保留全部非秘密详细信息 |
| 修正/移除配置与双方并发修改 | 保存前版，比较出冲突候选，不自动作业务裁决 |
| 维护端与Ego联通 | 四类读写按同一v3契约工作；错项目隔离及可选知识行为保持 |
| 未获准的真实环境操作 | 只完成合成验证；登记资料和读到入口不构成执行授权 |

实现后按改动范围做工程回归及合成联通；不把工程通过写成实际账号有权或真实业务通过。
