# 项目通用知识数据规范 v1

> 本文保留v1历史设计。当前开发采用[轻量v3设计](project-knowledge-lightweight-design.md)与当前JSON Schema，不按本文转换旧资料。

日期：2026-11-02。**设计已确认并形成格式 v1 实现。** 外部契约源为 [JSON Schema](../schemas/project-knowledge.schema.json)，精确字段及工具请求见[运行指南](../skills/project-knowledge-maintainer/references/format-and-tools.md)；运行时另校验跨文件引用、来源和变更依据。沿用原设计文件名，本文是双方共享的语义说明。

维护方法见[维护设计](v0.1.9-requirements-and-design.md)和[初始化与首次建库设计](initialization-and-first-build-design.md)，读取方法见 Ego 的[使用与检索设计](https://github.com/99Like-wjj/ai-autonomous-testing-ego-lite/blob/f437c64/docs/v0.1.9-project-knowledge-use-design.md)。本约定负责知识文件的含义，不规定团队必须使用何种分支审批流程。

## 1. 文件布局与最小信息

| 文件/对象 | 建议内容 | 用途 |
| --- | --- | --- |
| `knowledge.json` | `knowledgeFormatVersion`、`knowledgeId`、`projectId`、显示名称、`createdAt`、`scopes` | 描述项目/知识身份、实际创建时间、规范及范围，不含每次变化都要更新的全库修订号 |
| `topics/<topic-id>.json` | 通用主题 ID、名称/别名、适用业务/功能范围、相关规则与准备知识、必要索引及问题 | 只整理可复用知识，供按任务查找与团队分开维护，不是每功能一份规格 |
| `sources/<source-id>.json` | 确定版本资料的 ID、名称、`documentId`、资料版本/日期、定位、可得 SHA 和局限 | 陈述能定位到哪份资料的哪个版本；不复制原始资料全文 |
| 条目 `entry` | 稳定 ID、类型、名称/别名、陈述集合 | 类型可含 feature、role、identity、flow、object、experience、api，接口不强制存在 |
| 陈述 `statement` | 稳定 ID、文本、scope、可信类别、生命周期、来源引用、`updatedAt`、`changeReason`、必要关系/问题引用 | 状态和更新依据落实到可以独立引用的一段知识 |
| 问题 `issue` | 稳定 ID、类型、关联陈述、原因、双方依据或缺口、解决依据（若有） | 缺失、过时、待审及业务冲突可明确表达，与测试四态分开 |

同一条目只在一处维护。公共角色或对象按需要显式引用，不复制成几套独立正文。主题内可包含多个类型，但这些类型不是要求逐功能建模的清单，接口只保留有复用价值的约定或资料指引；初始不要求为每种类型建立目录或空文件，也不把每句话拆成陈述或文件。

功能索引仅简要说明用途、入口、共用前提及资料定位；不复制字段校验、页面细节、特殊分支、完整流程或用例。通用规则存在特例时只保存适用边界与原文指引。未知前提不等于无需前提；真正影响公共知识的未知写缺口，范围外的功能细则不逐项生成缺口清单。身份仅记录别名、角色及范围，不包含密码、Token、Cookie 或会话文件引用的实际秘密值。

有效空库允许只有合法 knowledge.json，无主题、无来源，topics/sources 目录可缺省；scopes 可为空，含义是范围尚未登记，不是全环境适用。createdAt 在初始化时生成，重复初始化不刷新。读取端须区分身份/结构有效、知识内容为空与本次测试资源已就绪，不能互相代替。

## 2. 项目、范围与标识

- `knowledgeId` 标识这套知识资产，`projectId` 标识业务项目；名称用于阅读，不用于判定身份相同。
- scope 明确环境、应用版本及必要的租户/部署说明。未知版本明确为未知，不隐含“所有版本均适用”。跨环境共用须明确声明，不能自动套用。
- 主题、条目、陈述、来源和问题都有稳定 ID。改名、排版、文件位置或数组顺序变化不改 ID；废弃 ID 不复用，不靠多人争用的连续编号分配。
- 条目/陈述 ID 不以文件路径为身份；同一项目范围内检查唯一性，以便移动主题后仍能追踪。
- 普通知识关系在本知识库内引用，不提供跨项目自动关联。同名角色、同名入口不能自动视为同一对象。

## 3. 可信类别、生命周期与问题

| 维度 | 建议值 | 含义 |
| --- | --- | --- |
| `knowledgeState` | `confirmed_rule` / `observation` / `pending` | 有明确有效依据的规则；某条件下实际观察；尚未确认的解释或信息 |
| `lifecycle` | `active` / `superseded` / `retired` | 当前适用；被明确替代；已退出，保留原因及必要替代引用 |
| 关联问题 | `conflict` / `stale` / `needs_review` 等 | 原来确认的规则也可能被新来源影响，不能只凭类别就用于当前判断 |

有效规则资料可由用户指定；AI 忠实整理不要求逐句重复批准。资料权威性、版本或含义未知时标 pending。规则与观察混在一句时需要拆分；观察较新、重复出现均不自动升级为规则。

过时判断依赖已知版本变化、有效期或明确维护依据，不设通用的自动过期天数；没有发现变化不证明仍正确。冲突关闭记录确认依据，Git 合并通过不自动关闭业务冲突。

## 4. 来源与更新时间

陈述的 `sourceRefs` 指向确定的 source ID，并保留章节、页码、消息或观察位置。来源记录要能区分同一份需求的不同版本；新版资料使用新的版本来源 ID，旧 ID 不能悄悄改指新版。

最小追溯关系为：**陈述 ID → 当前内容与更新时间/原因 → 来源 ID → 资料名称、版本/日期和具体位置 → Git 中的历史变更**。

| 时间/版本 | 表达什么 | 不代表什么 |
| --- | --- | --- |
| 来源版本、资料发布时间 | 整理依据是哪版、何时发布 | 后发布的资料一定适合本次环境 |
| `effectiveAt`（适用时） | 有来源支持的规则生效时间 | 文件修改时间或资料导入时间 |
| 陈述 `updatedAt` | 这条知识内容或依据最后一次实质修改时间 | 规则必然更正确、更权威 |
| 可得的 Git 作者/提交者与提交时间 | 文件变更及其提交历史 | 有权人员已确认业务规则 |

时间使用带时区的格式；未知日期/身份/版本如实注明，不能用本次时间补造。未变化陈述不因重新整理整个文件就统一刷新更新时间。纯排版变化交给 Git 记录，不伪装成规则更新。

来源不可访问或原件无 SHA 时保留可得定位和局限；不编造指纹。来源也可能是明确的用户确认记录，不强迫所有材料必须有文档版本号。

## 5. 通用主题、适用范围与按任务检索

主题提供稳定 ID、名称、适用业务/功能范围和可选别名/标签。例如完全合成的“对象归属与数据范围”主题可被登记、借用、归还等功能共用；某业务功能通过简要入口索引与适用范围关联，不需要把各功能细则全部收录。共同适用范围须有来源依据，不能因为两个功能相似就扩展规则。

重要关系也是带范围、状态与来源的陈述，可用 `requires`、`uses_role`、`operates_on`、`affects`、`navigates_to`、`related_to` 等明确含义表达。`related_to` 只说明关联，不推导前置步骤。

使用方可按当前任务的业务/功能定位相关公共主题，再按需读取规则正文、必要索引和显式关联，不能只依靠标题碰巧含某个词。默认结果用短摘要和精确引用，需正文或指定主题全量时再展开，不默认将全库、全业务规格或整份来源文档加入上下文。关系只保留复用所必需的信息，不追求完整知识图谱；展开时保留含义与状态及可见的数量/深度边界。

资料缺失、命中截断和坏引用须显示；刻意不收录的功能细则按原文指引读取，不当作建库缺陷。命中相关公共规则不等于覆盖了该业务全部真实规则，不设已收录百分比或虚构覆盖完整性。

## 6. 知识版本与精确读取来源

数据格式建议从 `knowledgeFormatVersion: 1` 起。内容历史使用 Git，取消上一稿的顺序 revision 文件和当前修订指针。查询/交接回执应包含：

- 规范、knowledge/project 身份、实际 scope、选定通用主题及其业务适用范围。
- 可得的完整 Git commit，及工作区是否有未提交/未合并内容；不知道时明确 unknown。
- 本次实际读取文件内容的 SHA-256；可用受管理文件路径与 SHA 的有序集合生成整体内容指纹，不把 mtime 当内容版本。
- 使用条目/陈述 ID、相对位置、所需来源与状态、诊断和截断范围。

Git commit 和内容指纹由读取工具生成回执，不写回其自身所标识的知识文件。未提交内容存在时，commit 只能标识其基线，不能单独代表实际读取内容；草案必须同时保留实际内容指纹和提示。

有 Git 时可读取显式指定的本地提交；没有 Git 的导出副本也能按文件格式读取，但缺少历史或远端新旧信息时必须声明。规范本身不要求调用 Coding API。某分支的时间更大不能自动裁定它取代另一分支，也不能证明规则适用于当前测试。

## 7. 有效性与互通要求

写入端检查 JSON、必需元数据、身份/范围、稳定 ID 唯一性、来源、关系和失效引用。读取端重复检查必要约束，不能只信文件来自维护 Skill。结构错误与业务冲突分开：前者不能成为有效条目，后者可结构化保存并阻止将争议内容当确定预期。

不支持的格式版本明确报错，不猜字段或自动降级。项目/scope 不匹配停止使用该库，局部缺失或坏条目明确影响，独立的有效知识仍可使用。整个身份文件损坏或内容完整性无法成立时，不伪称仍可信任整库。

两方采用同一套完全合成的正反例，核对规范版本、契约副本 SHA 及状态解释。维护仓库持有正式契约源；Ego 后续随运行包携带固定副本，无需运行时安装维护 Skill、下载契约或访问其源码仓库。

当前支持格式 v1，其他格式明确拒绝，不提供迁移或兼容读取。实际联通与验收范围见[开发自测](development-validation.md)。软件版本、知识数据格式和业务知识 Git 版本分别管理；格式调整不授权删除任何历史文件。
