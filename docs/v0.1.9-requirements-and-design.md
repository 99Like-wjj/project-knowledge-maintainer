## 1. 结论与文档归属

需求可行。团队共用、追溯依据、协助解决冲突及按业务检索都是必要能力，并不要求建立知识管理平台。需要调整的是：**时间戳用于追溯，不能单独裁定最新有效规则；版本历史优先复用 Git，不再自行维护整库修订系统。**

文档按职责存放，不把两方设计混成一份：

| 责任与内容 | 设计位置 |
| --- | --- |
| 知识初始化、首版创建、增量维护、团队版本与冲突处理 | 本文及[初始化与首次建库设计](initialization-and-first-build-design.md)，位于 project-knowledge-maintainer |
| 唯一共享格式与知识语义 | 本仓库[数据约定讨论稿](data-contract-draft.md)，创建端与读取端共同遵守 |
| Ego 按业务检索、使用知识、通用经验优化与测试侧验收 | Ego 仓库[知识使用与检索设计](https://github.com/99Like-wjj/ai-autonomous-testing-ego-lite/blob/f437c64/docs/v0.1.9-project-knowledge-use-design.md) |
| Ego 当前实现与经验审核依据 | Ego 仓库[设计前现状核对](https://github.com/99Like-wjj/ai-autonomous-testing-ego-lite/blob/f437c64/docs/v0.1.9-current-state-review.md) |
| 未来某个业务项目的真实资料与知识 | 用户确认的独立知识目录/公司内部知识仓库，不进入两个通用 Skill 源码仓库 |

上述跨仓库链接固定到本次核查的 Ego 开发提交；未来分发的 Skill 必须自包含，不依赖这些开发设计链接。共享数据约定只保留一个权威设计源，另一方引用并随运行包携带确定版本的契约。

## 2. 需求覆盖与能力边界

| 需求 | 推荐处理 | 主要限制 |
| --- | --- | --- |
| 初始化与首次创建跨项目知识库 | 支持无资料空库；从资料筛选项目内通用规则与准备知识，功能仅保留轻量索引 | 不展开每个功能的细化规则；资料不足或没有适合内容时可保留空库 |
| 规则、观察、待确认可区分 | 状态落到具体陈述，保留来源、适用范围和失效/冲突信息 | 观察多次或较新不等于成为业务规范 |
| 根据新资料增量维护 | 定位来源与显式关系，提出变更及受影响范围，按有效依据修订 | 引用只能确定直接影响候选，语义影响仍由 AI 核对 |
| 团队通过 Git/Coding 共享 | 文件适合普通 Git 管理，利用分支、提交、差异和合并 | 不在 Skill 中重造版本控制、公司权限或代码托管平台 |
| 处理版本冲突 | 使用 Git 的共同基线/双方差异，AI 协助整理，工具复核结构及引用 | 业务规则冲突不能机械选一方 |
| 追溯每条经验 | 稳定 ID、更新时间、更新原因和精确来源；完整历史由 Git 保留 | 时间新不证明适用、正确或已获确认 |
| 按业务找适用知识 | 格式提供通用主题、适用业务范围、别名和必要关系；Ego 只读查相关公共规则及来源指引 | 单功能细则按任务读原文，不默认全量加载或入库 |
| 原有通用经验与测试回归 | 由 Ego 项目维护对应设计和检查，联通时使用维护端真实合成产物 | 文档更多、结构通过不证明测试效果提高 |
| 保护真实资料 | 通用仓库仅含通用实现和完全合成示例；公司知识放独立内部仓库 | 私有 GitHub 工具仓库仍不能接收真实知识 |

### 入库范围：项目内通用规则与准备知识

根据用户补充，本库不做逐功能需求规格库。优先整理项目内跨功能可复用的角色/数据范围、公共业务约束、环境约定、通用准备依赖和项目经验；跨项目的一般测试方法仍在 Ego 通用经验中。功能地图只保留简要用途、入口和资料定位。

字段必填/长度/精度、页面细节、单功能特殊分支、完整功能流程及用例保留在原始需求或当次测试资产中。通用规则的例外只保留适用边界与原文指引，不扩展为整套功能细则。范围外细则不逐项登记为知识缺口，避免用缺口清单变相复制全量需求。

选择哪些内容值得沉淀由 AI 根据实际复用价值判断，不设固定条目数或强制录入清单。Ego 按任务读取相关通用知识和所需原文，不默认载入全库或整份需求。

## 3. 轻量存储方案：按通用主题组织，Git 保存历史

上一稿“整库 JSON 修订 + 当前版本指针 + revisions 目录”更偏向单机维护。团队共享后它会引入集中的文件修改点及独立修订号管理，因此本次设计调整为以下当前文件布局：

```text
<独立业务知识目录/内部知识仓库>/
  knowledge.json                知识/项目身份、规范版本、适用范围
  topics/
    <topic-id>.json              一个通用主题的规则、必要索引、关系与问题
  sources/
    <source-id>.json             一份确定版本资料的来源说明
```

按有意义的通用知识主题拆分，不要求给每个功能建文件，也不为每句话生成文件。相同规则只维护一份，按需标明适用业务或功能范围；读取端按约定目录定位文件，团队用普通 Git 管理经审查纳入的文件，无需每次修改内容都刷新一份全库指针或索引。稳定排序和排版减少纯格式冲突。

JSON 作为唯一可维护知识数据，段落文本可自然表达；Markdown 是按需生成的阅读投影，不与 JSON 各自维护事实。输入依然可以是自然语言、文档或截图，不要求用户手填 JSON。数据库、向量库、服务和自研合并引擎均不引入。

知识格式本身不依赖 Coding API 或 Git 元数据。首次可以形成文件草案；需要维护历史时，推荐直接使用本地 Git。正式更新前确保前版已由 Git 或明确保留的外部副本保存，不覆盖唯一前版。没有 Git 历史的文件可以读取，但不得声称完整版本可追溯；本版不为此另建第二套历史管理工具。

原始资料、凭据、运行报告和截图不自动加入知识仓库。阅读投影、缓存和测试运行摘录默认放在独立私有工作目录，避免成为团队合并对象。真实存储位置、公司知识仓库地址与上传范围以后明确，本轮不创建或连接它们。

## 4. 版本标识与来源追溯

版本分成三类，避免用一个“版本号”承担所有含义：

| 层次 | 推荐标识 | 用途 |
| --- | --- | --- |
| 数据规范 | `knowledgeFormatVersion` | 两个 Skill 是否能一致解析字段和语义 |
| 知识文件集合 | 已知完整 Git commit；实际内容 SHA-256 | 精确说明当次读取的是哪个文件状态；未提交内容标为本地草案 |
| 某条知识及其依据 | 稳定 statement ID + 来源版本/定位 + 更新时间/变更原因 | 找到哪条经验因哪份资料、何时被修改 |

每条重要陈述至少保留更新时间、变更原因及来源引用。来源说明记录资料名称、版本或日期、章节定位和可得的 SHA；某份资料出了新版，新增该版本的来源记录，不悄悄把旧 source ID 改指新版。历史陈述的来源定位因而不会被改写。

需求/手册的发布时间、规则生效时间和知识整理时间含义不同，分别记录已知值；统一用带时区的时间表达，未知明确留缺口。Git 作者/提交者及提交时间可辅助追溯，不当作业务审批的身份证明。当前提交号由工具读取后写在查询/交接回执中，不回填到正在被该提交追踪的文件，避免循环更新。

“最新”以本次明确选择的团队分支/提交为文件基线；“最新有效规则”还需核对环境、应用版本、来源权威性和确认状态。两个并行分支上的修改可能都需要保留，不能按时间戳较大的一条覆盖另一条。Git 的提交关系与时间排序也不是一回事。[Git 官方提交排序说明](https://git-scm.com/docs/git-log#_commit_ordering)

Ego 侧必须区别已提交状态、未提交草案、合并未完成及远端状态未知。未获取公司远端变化时，只能说当前本地基线，不能宣称它是公司平台上的最新内容。

## 5. 冲突处理：Git 合并与知识判断分工

维护 Skill 要能协助处理冲突，但不把它做成新的 Git 客户端平台。适用任务中由 AI 使用现有 Git 命令读状态、差异和共同基线；轻量工具负责结构、稳定标识、来源及引用检查。未请求同步时不自动拉取、推送或改变远端配置。

| 冲突/变化 | 建议处理 |
| --- | --- |
| 不同通用主题文件各有修改 | 利用 Git 合并，之后检查跨文件引用和业务适用范围 |
| 同一文件不同条目修改 | 按共同基线与稳定 ID 核对双方增删改；可合并互不矛盾的改动，保留双方来源 |
| 同一条陈述被改成不同含义 | 比较原文、双方新文、需求版本、环境与来源；能按明确有效依据解决时给出说明，依据不足则保留业务冲突 |
| 一方删除/下线，另一方修改 | 不直接丢弃任一侧；核对下线范围、来源和关联，失效知识保留状态及原因 |
| 新手册与旧规则矛盾 | 资料优先级或适用版本未明确时，不以文档时间自动决定正确规则 |
| 新测试观察与正式规则矛盾 | 新增 observation 及差异问题，不能把规则改为当前页面行为 |
| 只有更新时间等元数据冲突 | 在业务内容与来源均保留的前提下整理元数据，不把较大时间当作业务合并方案 |
| Git 显示无文本冲突，但不同文件互相矛盾 | 仍需引用校验及 AI 对受影响规则/关系的语义复核 |

Git 冲突时可取得共同祖先、本方与另一方三个版本；Git 的文本合并能力由现有 Git 提供。[Git 官方合并说明](https://git-scm.com/docs/git-merge#_true_merge)

区分两种未解决状态：文本/结构冲突会使有关文件不可读取，必须先修成合法文件；业务冲突可以结构化保存双方陈述与待确认问题，文件可正常共享，但不能把争议内容作为确定预期。Git 合并结束、JSON 可解析不等于业务冲突已解决。

工具不自动判断哪份需求更权威，不默认使用 ours/theirs 或最后写入覆盖，不强推、不重写历史。关键冲突关闭保留确认依据；已有有效新资料和维护授权足够时，不重复逐条审批。提交、同步与上传仍按具体任务授权和内容审查执行。

## 6. 创建与维护方法

初始化和首次建库分别细化在[独立设计](initialization-and-first-build-design.md)，可由一个自然语言请求连续完成。

- 初始化：确认项目与保存位置，建立稳定身份和最小合法空库；无资料也可完成，同项目重复调用不改旧文件。
- 首次建库：从授权资料中选择项目通用规则与准备知识，保留状态、范围、来源及必要索引；不逐功能展开细则。资料不足时可交付部分知识或保留空库，并说明边界。
- 增量维护：保留既有身份和历史，根据新资料修订受影响公共知识；已有库不因接到“新建”描述就重新覆盖。

没有接口文档仍可整理其他可信内容；截图不证明服务端权限，历史缺陷不变成正确预期。真实环境探索另按当次授权进行。

更新时读取已知基线和新资料，结合来源与反向关系定位影响；整理差异，核对冲突、失效和引用，保留变更依据。重要业务含义不明确时交付待确认草案，不为了文档完整而猜测。

本地保存使用当前文件指纹防止覆盖其他人的新改动，暂存后校验并读回，再替换本次明确修改的文件；跨文件更新需要写入期间标识与一致性检查。失败如实报告，不能把半完成更新标为有效共享版本。Git 并发分支由 Git 协调，本地锁只处理单机写入，不提供跨机器分布式锁。

恢复写入或合并前检查实际状态，不盲目重放、重置或覆盖他人未提交内容。来源、规则内容与关系是否真实仍由 AI 核对，工具只处理确定性文件事务。具体操作方法由 AI 根据任务选择，不固定成强制阶段流程。

## 7. 与 Ego 的交付约定

维护端按[共享数据约定](data-contract-draft.md)生成知识；Ego 按[使用方设计](https://github.com/99Like-wjj/ai-autonomous-testing-ego-lite/blob/f437c64/docs/v0.1.9-project-knowledge-use-design.md)自行检索、读取与使用，不调用维护 Skill。

共享格式必须表达通用主题、适用业务/功能范围及别名、精确来源、状态与必要关系，让 Ego 按任务找到适用公共规则、准备知识和轻量入口索引；单功能细则通过资料定位按需读取。不能以“检索完整”为由把全部功能需求搬进知识库。

同一组合成资料用于创建、更新、Ego 读取及冲突场景；规范源由维护仓库持有，Ego 固定携带经核对的契约副本。软件版本、数据规范版本和公司业务知识版本分别管理。

## 8. 隐私与既有数据影响

这里有三种不同仓库：维护 Skill 的通用源码仓库、Ego 的通用源码仓库、未来公司内部的业务知识仓库。真实知识只可能进入用户明确批准的内部业务知识仓库，绝不因此进入当前 GitHub 工具仓库。团队共享的具体权限与资料上传许可另行确认，不因公司内部可见就自动上传全部原始资料。

知识只保存必要身份别名和角色说明，密码、Token、会话等访问配置独立提供。日志、摘录和提交内容也须检查；忽略规则不能替代逐文件审核。仓库示例只允许完全合成内容，不用真实资料改名或脱敏代替。

这次只修改设计。上一稿尚无真实知识产物，不存在格式迁移；真实资料、旧运行和历史验证记录均不变。未来采用 Git 保存知识历史，不删除已存在的独立历史记录。

## 9. 验收与实现边界

| 验收场景 | 应看到的行为 |
| --- | --- |
| 空库初始化与重复/异常调用 | 见[初始化验收](initialization-and-first-build-design.md#9-验收设计)，身份与文件不被覆盖 |
| 两组完全合成项目资料创建 | 同一能力复用、身份不串用；仅沉淀通用知识与必要索引，部分资料缺失可见 |
| 大量功能细则混入输入 | 不逐功能入库或生成细则缺口清单；Ego 默认只取得相关公共知识和原文指引 |
| 某业务知识用于 Ego 测试 | Ego 不加载维护 Skill 即能取得适用通用规则、共用角色/数据约束及必要入口，状态和来源保留 |
| 新版资料调整入口或下线功能 | 更新后新内容可使用，旧内容失效和引用影响可识别 |
| 两个本地分支并行维护 | 不同主题、同一条目冲突、修改/下线冲突均可复核，不丢失任一方依据 |
| 时间较晚但来源旧/环境不同 | 不被自动选为最新有效规则 |
| 无 Git 文本冲突但业务矛盾 | 仍显示未解决业务冲突，不冒充确认结论 |
| 脏工作区、未合并、未同步远端 | 明确当次读取内容及局限，不把本地内容标成团队最新正式知识 |
| 缺条目、断引用、坏数据、错项目/范围、不支持格式 | 明确影响，可信独立部分仍可使用，不静默猜测 |
| 无知识库、无接口资料、状态待确认 | 可执行部分继续，关键判断缺口保留 |
| 隐私与原能力 | 完全合成材料、逐文件审核；Ego 相关工程回归与 AI 行为场景分别记录 |

开发先完成维护端创建→Ego 按业务读取→更新→再次读取，再在本地 Git 合成仓库验证团队并行/合并；不需要先接 Coding 平台。用户已授权代码、共享 schema 和开发自测；安装分发、远端推送与正式发布另按后续任务进行。

工程和合成验证的实际结果单列记录，不能把实现计划写成验收结果。“测试效果提高”仍须同目标、同资料和已知模型配置下的行为证据支持。

## 10. 本次建议审核的取舍

建议确认：按职责分开文档；知识限于项目内通用规则与准备信息，功能细则留原文；按通用主题组织 JSON；初始化与首次建库可独立或连续执行；Git 保存历史，不另建整库修订管理；来源可追溯；维护 Skill 协助冲突分析，Ego 按任务检索。保持来源状态、授权边界及历史记录保护。
